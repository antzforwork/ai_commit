# Git Semantic Commit

Skill untuk membuat commit message git dengan format **semantic commit**, tanpa embel-embel atribusi AI apa pun.

## Format Commit Message

```
<type>(<scope>): <description>

[optional body]
```

- **type** — jenis perubahan, huruf kecil semua. Pilihan yang valid:
  - `feat` — fitur baru
  - `fix` — perbaikan bug
  - `docs` — perubahan dokumentasi saja
  - `style` — perubahan format/style code (spasi, titik koma, dll), tanpa mengubah logic
  - `refactor` — perubahan code yang tidak menambah fitur atau memperbaiki bug
  - `perf` — perubahan yang meningkatkan performa
  - `test` — menambah/memperbaiki test
  - `build` — perubahan build system atau dependency
  - `ci` — perubahan konfigurasi CI/CD
  - `chore` — pekerjaan rutin lain yang tidak masuk kategori di atas
  - `revert` — membatalkan commit sebelumnya
- **scope** — nama fitur/halaman/modul yang terdampak, singkat dan huruf kecil (contoh: `login`, `checkout`, `navbar`, `api-user`). Jika perubahan terlalu luas untuk satu scope, scope boleh dihilangkan: `fix: ...`.
- **description** — ringkasan singkat, imperative mood, huruf kecil di awal, tanpa titik di akhir. Contoh: "perbaiki validasi email saat register".

### Batas Panjang Judul & Penggunaan Body

- Baris judul lengkap (`type(scope): description`) **maksimal 50 karakter**. Ini adalah konvensi standar git agar judul tetap ringkas dan mudah dibaca di `git log --oneline`.
- Jika 50 karakter tidak cukup untuk menjelaskan perubahan, **jangan** memperpanjang baris judul — pindahkan detailnya ke body commit (paragraf setelah baris judul, dipisahkan baris kosong).
- Body sebaiknya menjelaskan **apa yang berubah** dan **kenapa** (bukan sekadar mengulang judul), khususnya untuk perubahan yang tidak trivial. Semakin jelas body menjelaskan perubahan, semakin mudah dipahami saat review atau saat melihat riwayat commit di kemudian hari.

### Contoh

```
fix(login): perbaiki validasi email saat register
feat(checkout): tambahkan opsi pembayaran e-wallet
refactor(navbar): sederhanakan logic dropdown menu
docs(readme): update instruksi instalasi
chore(deps): update versi axios ke 1.7.0
```

## Aturan Krusial: Tanpa Atribusi AI

Commit message **TIDAK BOLEH** mengandung apa pun yang menyebutkan AI/Claude/model, termasuk namun tidak terbatas pada:

- `Co-Authored-By: Claude ...` atau nama model apa pun (Claude Sonnet, Claude Opus, dll)
- `Generated with Claude` / `Generated by AI` / sejenisnya
- Tautan `noreply@anthropic.com` atau domain Anthropic lainnya
- Emoji atau footer yang biasa ditambahkan oleh tooling AI (misal 🤖)

Commit message harus terbaca murni seperti ditulis oleh developer manusia — hanya berisi `type(scope): description` (dan body opsional jika relevan), tanpa footer tambahan apa pun.

## Langkah Kerja

1. **Cek status & diff** — jalankan `git status` dan `git diff` (atau `git diff --staged` jika sudah di-stage) untuk memahami perubahan apa yang terjadi. Jangan menebak isi commit tanpa melihat diff-nya.
2. **Stage perubahan jika perlu** — jika ada file yang belum di-stage dan relevan dengan permintaan user, jalankan `git add <file>` (tanya dulu ke user jika tidak yakin file mana yang dimaksud — commit adalah aksi yang mengubah riwayat repo, jadi pastikan file yang di-stage benar).
3. **Tentukan type & scope** — berdasarkan isi diff, pilih type yang paling sesuai dan scope yang mencerminkan fitur/halaman yang berubah.
4. **Susun description** — singkat, jelas, imperative, dalam bahasa yang sama dengan yang dipakai user (biasanya Bahasa Indonesia jika user menulis dalam Bahasa Indonesia).
5. **Commit** — jalankan:
   ```
   git commit -m "type(scope): description"
   ```
   Untuk body multi-baris, gunakan beberapa flag `-m` tambahan (masing-masing paragraf terpisah), TANPA menambahkan trailer/footer apa pun yang menyebut AI. Tidak perlu menampilkan/meminta persetujuan judul & body commit terlebih dahulu ke user — begitu user minta commit, langsung commit apa yang berubah.
6. **Tunjukkan hasil** — setelah commit berhasil, tampilkan commit message final ke user (misalnya via `git log -1`) supaya mereka bisa cek.

## Menangani Beberapa Perubahan Sekaligus

Jika diff mencakup beberapa perubahan yang tidak berhubungan (misal fix bug di satu halaman + tambah fitur di halaman lain), sarankan untuk split menjadi beberapa commit terpisah dengan `git add -p` atau staging per file, masing-masing dengan semantic commit message sendiri — daripada memaksakan satu commit besar dengan type yang tidak akurat.

## Setelah Selesai Mengerjakan Task

Ini trigger terpisah dari alur "user minta commit/push" di atas — dilakukan tanpa diminta:

- Begitu selesai mengerjakan sebuah task coding (menambah fitur atau memperbaiki bug), **jangan langsung commit sendiri**. Tanya dulu ke user: apakah hasilnya sudah sesuai/oke, dan apakah mereka ingin ini di-commit sekarang.
- Kalau user konfirmasi "ya"/"oke"/setuju, baru lanjut ke alur commit di atas (tentukan type & scope, susun message, langsung `git commit` tanpa perlu minta approval judul/deskripsi terlebih dahulu).
- Kalau user minta revisi, jangan commit dulu sampai user puas dan mengonfirmasi commit.

## Catatan

- Jangan pernah melakukan `git push` tanpa konfirmasi eksplisit dari user, karena ini mengirim perubahan ke remote yang bisa dilihat orang lain.
- Jika user punya konvensi commit khusus lain (misalnya JIRA ticket number di depan, seperti `[PROJ-123] fix(login): ...`), ikuti preferensi tersebut jika mereka menyebutkannya, selama tetap tidak menambahkan atribusi AI.
