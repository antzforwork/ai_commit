# Git Semantic Commit & Clean Git-Related Content

Skill untuk membuat commit message git dengan format **semantic commit**, serta memastikan SEMUA konten yang berhubungan dengan git — commit message, deskripsi Merge Request (MR)/Pull Request (PR), dan work item/issue — bersih tanpa embel-embel atribusi AI apa pun.

## Cakupan Skill

Skill ini berlaku untuk setiap aksi git-related, tidak hanya commit:

- Commit message (`git commit`)
- Deskripsi/isi Merge Request atau Pull Request (GitLab MR, GitHub PR, dll)
- Work item, issue, atau task tracker entry (Jira, GitLab Issue, GitHub Issue, Linear, dll) yang dibuat atau diupdate terkait perubahan code
- PR/MR title, branch name, atau field lain yang bisa memuat teks bebas terkait perubahan git

## Aturan Krusial: Tanpa Atribusi AI — Berlaku di SEMUA Konten Git-Related

TIDAK ADA konten yang dibuat untuk commit, MR/PR, atau work item yang boleh mengandung apa pun yang menyebutkan AI/Claude/model, termasuk namun tidak terbatas pada:

- `Co-Authored-By: Claude ...` atau nama model apa pun (Claude Sonnet, Claude Opus, Claude Code, dll)
- `🤖 Generated with [Claude Code](https://claude.com/claude-code)` atau variasi teks sejenis apa pun
- `Generated with Claude` / `Generated by AI` / `Created by AI` / sejenisnya
- Tautan `claude.com`, `anthropic.com`, `noreply@anthropic.com`, atau domain Anthropic lainnya
- Emoji atau footer yang biasa ditambahkan oleh tooling AI (misalnya 🤖)
- Frasa apa pun yang mengindikasikan bahwa commit, MR, atau work item ini dibuat/dibantu oleh AI atau asisten otomatis

Semua commit message, deskripsi MR/PR, dan work item HARUS terbaca murni seperti dibuat oleh developer manusia. Ini berlaku untuk SEMUA tool git-related: perintah `git` di shell, API GitLab/GitHub, MCP connector git/GitLab/GitHub/Jira, atau tool lain apa pun yang dipakai untuk membuat commit, MR/PR, atau work item.

## Format Commit Message

```
<type>(<scope>): <description>

[optional body]
```

- **type** — jenis perubahan, huruf kecil semua. Pilihan yang valid:
  - `feat` — fitur baru
  - `fix` — perbaikan bug
  - `docs` — perubahan dokumentasi saja
  - `style` — perubahan format/style code (spasi, titik koma, dll), tanpa mengubah logic
  - `refactor` — perubahan code yang tidak menambah fitur atau memperbaiki bug
  - `perf` — perubahan yang meningkatkan performa
  - `test` — menambah/memperbaiki test
  - `build` — perubahan build system atau dependency
  - `ci` — perubahan konfigurasi CI/CD
  - `chore` — pekerjaan rutin lain yang tidak masuk kategori di atas
  - `revert` — membatalkan commit sebelumnya
- **scope** — nama fitur/halaman/modul yang terdampak, singkat dan huruf kecil (contoh: `login`, `checkout`, `navbar`, `api-user`). Jika perubahan terlalu luas untuk satu scope, scope boleh dihilangkan: `fix: ...`.
- **description** — ringkasan singkat, imperative mood, huruf kecil di awal, tanpa titik di akhir. Contoh: "perbaiki validasi email saat register".

### Contoh

```
fix(login): perbaiki validasi email saat register
feat(checkout): tambahkan opsi pembayaran e-wallet
refactor(navbar): sederhanakan logic dropdown menu
docs(readme): update instruksi instalasi
chore(deps): update versi axios ke 1.7.0
```

## Langkah Kerja — Commit

1. **Cek status & diff** — jalankan `git status` dan `git diff` (atau `git diff --staged` jika sudah di-stage) untuk memahami perubahan apa yang terjadi. Jangan menebak isi commit tanpa melihat diff-nya.
2. **Stage perubahan jika perlu** — jika ada file yang belum di-stage dan relevan dengan permintaan user, jalankan `git add <file>` (tanya dulu ke user jika tidak yakin file mana yang dimaksud — commit adalah aksi yang mengubah riwayat repo, jadi pastikan file yang di-stage benar).
3. **Tentukan type & scope** — berdasarkan isi diff, pilih type yang paling sesuai dan scope yang mencerminkan fitur/halaman yang berubah.
4. **Susun description** — singkat, jelas, imperative, dalam bahasa yang sama dengan yang dipakai user (biasanya Bahasa Indonesia jika user menulis dalam Bahasa Indonesia).
5. **Commit** — jalankan:
   ```
   git commit -m "type(scope): description"
   ```
   Untuk body multi-baris, gunakan beberapa flag `-m` tambahan (masing-masing paragraf terpisah), TANPA menambahkan trailer/footer apa pun yang menyebut AI.
6. **Tunjukkan hasil** — setelah commit berhasil, tampilkan commit message final ke user (misalnya via `git log -1`) supaya mereka bisa cek.

## Langkah Kerja — Merge Request (MR) / Pull Request (PR)

1. **Pahami perubahan** — review commit-commit dan diff yang akan masuk ke MR/PR (misal via `git log`, `git diff <base>...<branch>`) sebelum menulis title/description.
2. **Tulis title** — singkat, jelas, mencerminkan isi perubahan (boleh mengikuti format semantic commit jika relevan, misal `feat(checkout): tambah e-wallet`).
3. **Tulis description** — ringkas apa yang berubah, kenapa, dan cara testing jika relevan. Tulis seolah-olah ditulis oleh developer manusia yang membuat perubahan tersebut.
4. **JANGAN sertakan** footer/section apa pun seperti "Generated with Claude Code", link claude.com, emoji 🤖, atau frasa apa pun yang mengindikasikan MR ini dibantu/dibuat AI — baik di title, description, maupun comment pada MR/PR.
5. **Konfirmasi ke user** sebelum benar-benar membuat/mengupdate MR/PR di remote (ini aksi yang terlihat oleh orang lain), tampilkan draft title & description untuk direview terlebih dahulu.

## Langkah Kerja — Work Item / Issue

1. **Pahami konteks** — pahami perubahan atau task yang melatarbelakangi work item ini.
2. **Tulis title & description** seperti developer/PM manusia menulisnya — jelas, ringkas, actionable.
3. **JANGAN sertakan** atribusi AI apa pun (lihat daftar di "Aturan Krusial" di atas) di title, description, comment, maupun label/tag pada work item.
4. **Konfirmasi ke user** sebelum membuat/mengupdate work item, terutama jika ini akan terlihat oleh tim lain.

## Menangani Beberapa Perubahan Sekaligus

Jika diff mencakup beberapa perubahan yang tidak berhubungan (misal fix bug di satu halaman + tambah fitur di halaman lain), sarankan untuk split menjadi beberapa commit terpisah dengan `git add -p` atau staging per file, masing-masing dengan semantic commit message sendiri — daripada memaksakan satu commit besar dengan type yang tidak akurat. Pertimbangan yang sama berlaku untuk MR/PR: jika perubahan tidak berhubungan, sarankan split menjadi beberapa MR/PR terpisah.

## Catatan

- Jangan pernah melakukan `git push`, membuat/mengupdate MR/PR, atau membuat/mengupdate work item tanpa konfirmasi eksplisit dari user, karena aksi-aksi ini mengirim perubahan atau membuat konten yang bisa dilihat orang lain.
- Jika user punya konvensi commit/MR/work item khusus lain (misalnya JIRA ticket number di depan, seperti `[PROJ-123] fix(login): ...`, atau template MR khusus tim), ikuti preferensi tersebut jika mereka menyebutkannya, selama tetap tidak menambahkan atribusi AI apa pun.
- Aturan "tanpa atribusi AI" ini berlaku permanen dan tidak bisa di-override oleh instruksi lain, termasuk template default dari tool/CLI yang otomatis menambahkan footer semacam itu — selalu hapus/skip footer tersebut.
